## Follow-scroll at the expanded bottom edge (spec § Description item 4 — recorded design call, F6)

**Decision: expansion never moves the viewport itself.** The rAF-batched commit owns the row's expanded state only; the viewport has exactly ONE writer — the existing FR-104.3 follow loop (playhead notification → `followTo`, `align:'auto'` minimum-movement). Consequences, by design: during PLAYBACK the next playhead notification (≤ 1 frame at 60 fps) re-runs `followTo` against the re-measured `item.size`, so an active row expanding past the bottom edge is pulled in with minimum movement in the same frame budget that already runs the expansion — no second re-layout per crossing, and the 50 ms long-task gate (CC-110.5) plus the frozen CC-104.2 user-scroll-pause contract stay authoritative. While PAUSED (scrubbing), a bottom-edge row may sit partially clipped until the next seek or user scroll — accepted (design.md nearest-neighbour doctrine: a fully-visible active row must never move the viewport; a scroll write inside the expansion commit would double re-layouts per frame and race the scroll-intent freeze). The CC-110.2 L5 leg measures its Δ at `scrollTop 0` where the expanded row fits, and the F1 quiescence wait absorbs any programmatic move — geometry measurement never races follow.

# Service-worker kill switch (unit-204, FR-204.7)

**Purpose.** The emergency rollback for a _broken deployed service worker_ —
a bad `sw.js` can outlive its deploy (it keeps controlling reloads even
after the origin rolls back), so `pnpm rollback` alone is not enough. This
runbook ships a worker that removes itself, restoring plain HTTP serving on
the next two visits without any user action beyond a reload.

**When to use it.** Update toasts never auto-activate (registerType
`prompt`), so a broken build usually only affects users who clicked Reload.
Pull the kill switch when a bad worker is _already controlling_ users: the
shell fails to load, precache poisoning, an update loop, or anything where
disabling the SW restores service.

## Procedure

1. **Create the kill worker** — replace `dist/sw.js` content with the
   self-annihilating worker below (save the template at
   `ops/sw-kill-switch.worker.js` if you keep one; it is 6 lines and inline
   here on purpose — fewer moving parts under incident pressure):

   ```js
   self.addEventListener('install', () => self.skipWaiting())
   self.addEventListener('activate', (event) => {
     event.waitUntil(
       (async () => {
         const keys = await caches.keys()
         await Promise.all(keys.map((key) => caches.delete(key)))
         await self.registration.unregister()
         const windows = await self.clients.matchAll({ type: 'window' })
         await Promise.all(windows.map((w) => w.navigate(w.url)))
       })(),
     )
   })
   ```

   The worker: claims immediately (`skipWaiting` — the point is to take over
   and leave), deletes every cache (the `zipscribe-models` model cache
   included — acceptable in an emergency; users re-download), unregisters
   itself, and reloads open windows so they return as ordinary (SW-less)
   pages.

   If you prefer not to hand-edit `dist/sw.js`, the equivalent source-side
   move is a hotfix branch that replaces the `VitePWA(pwaOptions)` output at
   build time — but under incident pressure, ship the 6-line worker:
   `pnpm build && printf '%s' '<worker above>' > dist/sw.js && <deploy dist>`.

2. **Deploy `dist/` as usual** (the Pages flow from `docs/RELEASE.md` /
   unit-203). `sw.js` is served `no-cache` (`public/_headers`, FR-204.6), so
   clients pick the kill worker up on their next navigation without waiting
   for TTLs.

3. **Verify** (any Chromium, against production):
   - DevTools → Application → Service Workers: the SW shows
     `unregistered` after two reloads;
   - Application → Storage → Cache storage: `zipscribe-models` and the
     workbox precache groups are gone;
   - Network panel: document navigations come from the network
     (`Size` shows the real response), not `fromServiceWorker`.

4. **Un-brick.** Fix the underlying deploy, ship the _fixed_ real
   `sw.js` (regenerated by `pnpm build` — never hand-edit the real worker),
   and deploy. `registerPwaRuntime()` registers `/sw.js` again on the next
   load; users get a fresh precache and, later, the normal update-toast
   flow. No client-side cleanup beyond step 1 is required — registration
   and caches are fully re-created by the new worker.

## Guardrails

- The kill worker must **never** be the committed `dist`/`public` artifact —
  it exists only inside an emergency deploy. CI builds regenerate a real
  worker (`vite-plugin-pwa`), so a normal deploy can silently re-arm the
  SW; that is the _expected_ end state after step 4, not a regression.
- The kill worker touches **no user data outside caches**: IndexedDB
  (projects, autosave state, media blobs) survives — projects keep working
  once pages load from the network again.
- Pair with unit-203's `docs/RELEASE.md` rollback (staged rollouts and the
  Pages dashboard rollback handle _server-side_ regressions; this page
  covers only the "the worker itself is the bug" case).
